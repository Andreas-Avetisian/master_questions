# Name and describe the typical contents of a requirements specification.

## Requirements specification

A **requirements specification** describes the system from the **customer point of view**. It explains why the system is needed, what problem it solves, and what requirements the solution must satisfy.

The PM2 lecture distinguishes it from the **technical specification**, which is more supplier-oriented and describes what the system must do technically.

## Typical contents

## 1. Introduction

The introduction explains the basic frame of the document:

- purpose of the specification
- scope of the system or project
- definitions of important terms
- references to related documents

This section ensures that all readers understand what the document covers and what terminology is used.

## 2. Overall description

The overall description gives the big picture of the product or system:

- product perspective
- main functions
- constraints
- relevant assumptions or dependencies

This section answers what kind of system is being described and how it fits into its environment.

## 3. Specific requirements

This is the core of the requirements specification. It describes the concrete requirements the system must fulfill.

Typical categories are:

- **functional requirements**: what the system should do
- **non-functional requirements**: qualities such as performance, security, usability, availability, reliability, or maintainability
- **interfaces**: interactions with users, other systems, hardware, or software
- **features**: specific capabilities expected by stakeholders

Good requirements should be clear, measurable, and testable.

## 4. External interface requirements

External interfaces describe how the system interacts with its environment.

Examples:

- user interfaces
- hardware interfaces
- software interfaces
- communication interfaces

This matters because many misunderstandings happen at system boundaries.

## 5. System models (optional)

System models can be included when useful. They may show structure, behavior, workflows, data flows, or relationships between components.

This section is optional because not every requirements specification needs formal models, but diagrams can make complex requirements easier to understand.

## 6. Validation and acceptance criteria

This section defines how fulfillment of the requirements will be checked.

It should describe:

- verification criteria
- validation approach
- conditions for acceptance
- test or review criteria

Acceptance criteria are important because they make requirements measurable and reduce later disputes.

## 7. Version and date

The lecture explicitly lists version and date of the document. This is important because requirements change, and stakeholders need to know which version is valid.

## Why this matters

A good requirements specification is important because it:

- creates a common basis for all parties
- aligns team and client expectations
- avoids misunderstandings
- supports implementation
- supports time and budget planning
- keeps requirements traceable
- reduces project risk
- provides a basis for tests and acceptance

## Short summary

A requirements specification typically contains an **introduction**, **overall description**, **specific functional and non-functional requirements**, **external interface requirements**, optional **system models**, **validation and acceptance criteria**, and **version/date information**. Its purpose is to describe the system from the customer point of view and make expectations clear, testable, and traceable.
